# 模板方法模式 (Template Method Pattern)

## 定义
在父类中定义算法的骨架，将某些步骤的具体实现延迟到子类。模板方法使子类在不改变算法结构的前提下，重定义算法的某些特定步骤。

## 一句话本质
**父类定义流程框架，子类填充具体实现细节。**

## 核心组成

### 1. 抽象类 (Abstract Class)
- 定义模板方法（final）：固定算法骨架
- 定义基本方法：
  - **抽象方法**：必须由子类实现
  - **具体方法**：通用步骤，所有子类共享
  - **钩子方法**：可选步骤，子类可以选择性重写

### 2. 具体类 (Concrete Class)
- 实现抽象方法：提供特定步骤的具体实现
- 可选择性重写钩子方法：控制可选行为

## 关键特性

### 1. 模板方法必须是 final
```java
public final void makeBeverage() {
    // 防止子类改变算法结构
}
```

### 2. 抽象方法强制子类实现
```java
protected abstract void brew();
protected abstract void addCondiments();
```

### 3. 钩子方法提供可选扩展点
```java
protected boolean customerWantsCondiments() {
    return true;  // 子类可以重写来控制行为
}
```

## 优点
1. ✅ **封装不变部分，扩展可变部分** - 公共代码在父类，差异化在子类
2. ✅ **代码复用** - 相同的流程逻辑只需写一次
3. ✅ **行为统一** - 算法结构固定，不会因子类实现而改变
4. ✅ **符合开闭原则** - 新增子类不需要修改父类

## 缺点
1. ❌ **类数量增加** - 每个不同实现都需要一个子类
2. ❌ **基于继承** - 耦合度较高，违反组合优于继承原则
3. ❌ **灵活性受限** - 流程固定，无法运行时动态改变步骤

## 使用场景

### ✅ 适合使用模板方法
- 多个类有相同的算法结构，但某些步骤实现不同
- 需要统一控制算法流程，防止子类破坏算法结构
- 希望提取公共代码，避免重复

**典型场景**：
- 数据库访问：连接 → 执行 → 关闭
- 文件处理：打开 → 读写 → 关闭
- HTTP 请求：构建请求 → 发送 → 处理响应
- 测试框架：setUp → test → tearDown

### ❌ 不适合使用模板方法
- 需要运行时动态调整流程顺序
- 各个步骤需要独立复用
- 不希望使用继承

**此时考虑**：策略模式、管道模式

## 对比其他模式

### vs 策略模式
- **模板方法**：定义算法骨架，子类实现某些步骤
- **策略模式**：整个算法可替换，强调算法的完整性

### vs 管道模式
- **模板方法**：流程固定，基于继承，强调类型行为差异
- **管道模式**：流程可动态调整，基于组合，强调数据流转

### vs 工厂方法
- 都基于继承，但关注点不同
- **模板方法**：关注算法流程的复用
- **工厂方法**：关注对象创建的延迟

## 实际应用

### JDK 中的应用
- `java.io.InputStream` - read() 方法模板
- `java.util.AbstractList` - add(), remove() 等模板
- `java.util.AbstractSet` - 集合操作模板

### Spring 中的应用
- `JdbcTemplate` - 数据库操作模板
- `RestTemplate` - HTTP 请求模板
- `TransactionTemplate` - 事务处理模板

## 总结

模板方法模式通过将算法结构固定在父类，把可变部分留给子类实现，实现了代码复用和行为统一。它用"不灵活"换来了安全性和一致性，特别适合那些"流程绝对不能乱"的场景。
